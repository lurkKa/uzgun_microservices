# Обзор рефакторинга — 27 октября 2026

## Результат

В текущем Maven-проекте подготовлен один User API сервис. Корневой package
`com.uz.uzgun_microservices`, artifact `uzgun_microservices`, URL и operationId сохранены.
Ручка читает явное право обхода checkout, default false. Это согласованная пользователем политика,
а не реконструкция неизвестного внутреннего кода Uzum. Дальнейшие ручки пока не реализованы.

## Что изменено и почему

| Было | Стало | Практический результат |
|---|---|---|
| Общий UserService с проверкой всех ограничений | CheckoutPermissionService читает только grant | `false` не означает запрет покупки; нет случайной выдачи права всем подходящим покупателям |
| Endpoint зависел от риска и заполненности профиля | Отдельный модуль обычной eligibility, выключен по умолчанию | Отказ риск-сервиса не влияет на чтение grant; нет недоказанной зависимости в flow |
| Нет хранения bypass grant | V2 добавляет NOT NULL boolean DEFAULT FALSE | Старые и новые пользователи не получают право автоматически |
| Получение всей User entity | SELECT только нужного boolean по userId | Не читаются ненужные персональные поля; отсутствие пользователя отличается от false |
| Разрозненные packages, опечатка repositroies | user/api, application, domain, persistence; security; shared; checkout | Место для следующих use cases понятно; инфраструктура отделена от правил |
| Дублирующие envelope и пустой DTO | Один GenericResponse и record PermissionToCheckoutDto | Нет расходящихся моделей даты/ответа; сохранён JSON-контракт |
| Смешанный стек зависимостей | Boot 4 starters, Jackson 3, один Logback backend | Нет конфликтующих SLF4J providers; удалены H2 runtime, JJWT, MapStruct, HATEOAS, лишние overrides |
| Неявный порядок правил через annotations | Явный список локальных правил перед risk | Порядок детерминирован, ранний отказ не делает HTTP-запрос |
| Пустой risk response означал разрешение | Проверяется реальный JSON boolean | null, пропуск поля, строка, число, сломанный JSON и сетевые ошибки не дают разрешение |
| Circuit breaker зависел от AOP | Программное выполнение через breaker | Защита действует и в тестах, и при обычном создании адаптера |
| Общая security-инфраструктура внутри user | Отдельный security package, stateless JWT | Нет form/basic login, request cache; проверяются issuer/audience/expiry и CUSTOMER |
| Нечисловой/отрицательный sub | Только положительный users.id | Контроллер не выбирает пользователя из параметров клиента |
| Неопределённые HTTP-ошибки | JSON 401/403/400/503/500; WWW-Authenticate и Allow | Клиент получает стабильный контракт и корректные HTTP-заголовки |
| GET мог кэшироваться как обычный ответ | Cache-Control: no-store, без серверного cache | Следующий запрос видит отзыв grant |
| Только liveness и неполная наблюдаемость | Readiness с БД, Prometheus для OPS, trace, ECS в prod | Различаются живой процесс и готовность обслуживать запросы |
| Docker пропускал тесты | Сборка выполняет verify; отдельный CI с PostgreSQL | Нерабочие тесты не обходятся обычной сборкой образа |
| Только mock service tests | Unit, MVC, реальный HTTP risk, PostgreSQL/JWT integration | Проверяется поведение на границах, а не только создание DTO |

Удалены `AppTest` с `assertTrue(true)`, неиспользуемый `GenericResponseObject`, дублирующий
`GenericResponsePermissionToCheckoutDto`, пустой `dto.PreferredDelivery`. Существующие поля User,
enum и CustomerContactsDto сохранены для последующей работы с контактами.

## База и безопасность данных

V1 побайтно сохранена: это проверено относительно снимка до рефакторинга.
V2 добавлена отдельно. Рабочий Compose volume не удалялся и не мигрировался агентом.
Проверки использовали одноразовые базы. Гранты в рабочей базе не выдавались.
Нет нового публичного метода записи grant. Существующий JWT должен иметь числовой sub,
roles CUSTOMER и согласованный audience. Для инфраструктурных метрик требуется OPS.

Это не полная система управления доступом: механизм выдачи/отзыва grant, срок действия,
операторский аудит и синхронизация identity должны быть определены отдельно.
Сейчас grant хранится у пользователя; управление разрешено только доверенной процедуре БД.

## Границы готовности

Это проверенная основа для дальнейшей разработки и развёртывания, а не подтверждение работы
на реальном production-трафике. Не выполнены нагрузочные испытания, SLO, настройка настоящего
issuer/secret store/ingress, бизнес-аудит grants. Атлас описывает предложенный flow и явно
не доказывает обязательность последовательности запросов. Наши допущения перечислены в
[контракте и flow](checkout-permission.md).

При добавлении `POST /user/v2/order` право надо перечитать на сервере и согласовать, какие
ограничения оно обходит. Остатки, цена, оплата, идемпотентность и атомарность заказа не реализованы
и не могут считаться выполненными из-за успешного GET.

## Как продолжать

1. Настроить реальные issuer/audience и локальное окружение по README.
2. Выполнить `mvn clean verify -Pintegration` и `docker compose up --build -d`.
3. Следующую ручку добавлять отдельным use case в доменный пакет; сверять её схемы и flow с атласом.
4. Новые таблицы/колонки добавлять следующей Flyway-миграцией. Не менять применённые V1/V2.
5. Выделять самостоятельный микросервис только вместе с границей данных и независимым деплоем.

Коммиты, push и публикация не выполнялись. Git index не перестраивался: исходные staged/unstaged
изменения пользователя сохранены; новые перемещения видны в рабочем дереве.
